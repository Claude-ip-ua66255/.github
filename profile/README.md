<p>账号交接最容易出事的时间点，不是交接当天，而是交接前那几天。旧设备上的环境还在跑，新设备已经在配，两边的出口、时区、登录态互相打架，等到正式交接时问题一起爆出来。这篇按时间线写，把交接拆成前七天、前三天、前一天、当天、后二十四小时和第一周几个节点，每个节点该做什么、做到什么程度算完，都写清楚。这套流程我在团队里跑过几次，交接当天基本能一次过。</p>

<h2>一、交接前七天：先把要交接的东西列全</h2>
<h3>四类东西，一样都不能漏</h3>
<p>这一步听着像废话，但漏东西最多。至少要列四类：账号本身（含二次验证方式）、出口线路（编号与归属地）、客户端环境（时区、语言、插件配置）、操作约定（哪些动作要打招呼）。四类里最容易漏的是第四类，交接完新同事不知道该问谁，只能自己摸索，一摸索就容易出岔子。</p>
<h3>为什么一定要落到文档</h3>
<p>列完之后做一件事：把旧设备的配置导出成一份文档，别指望口头交代。文档里的字段和后面验收表要对得上，否则交接时还要来回确认。</p>

<h2>二、前三天：试用几条线，把干净度验掉</h2>
<p>新设备用哪条线，不要凭感觉挑。申请两三条试用线，分别指向同一个目标站点，跑同一套操作，记录表现。挑的时候别只看能不能连通，要看有没有验证页、延迟稳不稳、IP 是不是固定的。</p>
<h3>试用记录怎么记</h3>
<p>一条线一行，字段固定：线路编号、归属城市、连续五次请求是否同 IP、二十次请求里验证页出现次数、首字节延迟中位数。四项填完，谁好谁差一眼能看出来。</p>

<h3>不合适就换，别硬凑</h3>
<p>试用期就是用来否定的。三条线里有一条始终有验证页，直接排除，不要想着「配好了可能就好了」。线路的问题靠配置改不掉。</p>

<h2>三、前一天：把环境固定下来，别再动</h2>
<p>交接前一天，新设备的环境要定稿：时区、语言、客户端版本、插件列表全部确认，然后进入只读状态。这期间不要再装新插件，也不要升级客户端。任何改动都可能让第二天的首次登录表现异常。</p>
<p>同时把旧设备降频。旧设备如果还在高频跑任务，两条线同时活跃，等于给平台一个「同一批账号在两个地方活动」的信号。建议交接前二十四小时把旧设备的任务停掉，只保留必要的检查。</p>
<p>还有一点常被忽略：把新设备的系统时间同步开起来。系统时间漂移几百毫秒不显眼，但有些客户端会校验时间戳，偏差过大时表现为登录失败却没有任何错误码。交接前检查一次自动同步是否开启，顺手的事，能省掉一类很难查的故障。</p>

<h2>四、当天：按顺序做，不要跳步</h2>
<p>顺序是这样的：先连线路、再验 IP、再开客户端、最后登号。每一步都有明确的通过条件，不通过就停在这一步，别往下走。</p>

<p>第五步别省。很多人登进去看一眼觉得没问题就结束了，结果第二天跑任务才发现超时设置还沿用旧环境的 5 秒，一直报失败。</p>

<h2>五、后二十四小时与第一周：观察窗口</h2>
<p>交接后第一天，重点看三件事：有没有出现额外的验证、会话有没有中途掉线、日志里的出口 IP 是不是一直是同一条。这三件事都正常，基本可以认为交接成功。</p>
<p>第一周再看趋势。把新环境的失败率和旧环境同期比一比，差距在五个百分点以内算正常。如果明显更高，多半是某处细节没对齐，拿着交接文档逐项核对，比重新猜要快得多。价格方面，试用线路一般按天计费或免费，正式月租常见几十到两百元一条，仅供参考。</p>

<h2>常见问答</h2>
<h3>交接一定要停掉旧设备吗？</h3>
<p>答：建议停，至少降频。两边同时活跃，会让同一批账号看起来在两个地方活动，容易触发额外确认。短暂并行没问题，长期并行不建议。</p>
<h3>试用几条线比较合适？</h3>
<p>答：两到三条。一条太少没有对比，三条以上边际收益低，还增加验收工作量。三条里挑出一条当主用，一条备用就够了。</p>
<h3>交接当天登录被要求验证，是不是要重来？</h3>
<p>答：不用重来，但要停下来查。先核时区、语言、DNS 三项，再核出口 IP 是否和验收表一致。三项都对还反复验证，就换备用线路再试一次。</p>
<h3>交接文档要写多细？</h3>
<p>答：写到「照着做不用问人」的程度。至少包含线路编号、出口 IP、时区语言设置、客户端版本、常用任务的操作步骤、出问题找谁。篇幅不用长，字段齐就行。</p>
